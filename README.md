# 🕯 暖归 · 宠物善终服务预约告别与骨灰寄存平台

围绕**同一只宠物**，让宠物主人、客服、接送员、礼仪师、火化师、纪念品制作、财务和管理者在同一工单上协同，
全流程记录承诺时间、见证材料、费用变化与家属确认，敏感争议可追溯到具体交接节点。

- 后端：NestJS 11 + TypeORM + MySQL/MariaDB（端口 4000）
- 前端：Next.js 14 (App Router) + React 18（端口 3000）
- 数据库：本地免安装 MariaDB 10.11，**无需 root / docker / apt**，脚本自动下载到 `.local/`

---

## 一、本地启动

### 方式 A：Docker Compose 一键启动（推荐，免装数据库）

```bash
docker compose up --build
```

首次启动自动：拉起 MariaDB 10.11 → 后端建表并在空库写入演示账号 → 前端构建。
- 前端：http://127.0.0.1:3000
- 后端：http://127.0.0.1:4000
- 数据库：`localhost:3306`，库 `pet_aftercare`，账号 `petapp/petapp123`（数据在 compose 卷 `dbdata`）

> 容器仅在**空库**时自动播种；重置演示数据可执行：
> `docker compose exec backend npx ts-node scripts/seed.ts`

### 方式 B：一键脚本（本地免安装 MariaDB）

```bash
bash scripts/setup.sh   # 首次：下载 MariaDB → 建库建表 → 装依赖 → 写入种子账号与资源
bash scripts/dev.sh     # 启动：MariaDB + 后端 4000 + 前端 3000
```

打开 http://127.0.0.1:3000

### 方式 C：手动分步

```bash
# 1. 数据库（当前用户运行，数据在 .local/mysqldata）
.local/mysqlctl.sh start      # 启动（首次自动初始化、建库 pet_aftercare、建号 petapp/petapp123）
.local/mysqlctl.sh status     # 查看状态
.local/mysqlctl.sh stop       # 停止

# 2. 后端
cd backend
npm install
npm run seed                  # 建表（synchronize）+ 写入种子数据
npm run dev                   # http://127.0.0.1:4000

# 3. 前端（新终端）
cd frontend
npm install
npm run dev                   # http://127.0.0.1:3000
```

数据库连接可用环境变量覆盖：`DB_HOST / DB_PORT / DB_USER / DB_PASS / DB_NAME`。
若要连接已有的 MySQL，把这几个变量指向你的实例后直接 `npm run seed` 即可。

> 重置演示数据：`cd backend && npm run seed`（清空并重建业务数据）

## 四、已实现的需求场景

1. **客服确认方案**：系统按体重档位与服务选项生成建议报价（支持自定义总价），生成家属「服务方案确认」。
2. **调度排期**：一次排定接送员、冷藏暂存位、火化炉档期、告别室档期；火化炉/告别室同时段冲突会被拦截；重调度自动释放旧档期；按选项自动生成纪念品制作单。
3. **临时更改仪式时间**：家属发起改期申请 → 客服同意后告别室档期自动重排；驳回也留痕。
4. **体重与报价不符**：接送员接运复称后，按 20 元/kg 自动生成多退少补的费用变更，**必须家属确认**；存在未确认变更时火化环节被系统拦截。
5. **接送交通延误**：接送员上报分钟数与原因，承诺接运时间自动顺延，并在工单留言中通知家属。
6. **视频见证**：家属随时登记视频见证，火化完成时校验见证安排，证明中记录。
7. **纪念品制作失败处理（重点）**：爪印泥 / 毛发纪念瓶等制作失败时**立案**，平台关联**制作人、剩余可用材料、主人选择**，立即生成客服关怀回访；客服据此提供**重做 / 退款 / 替代纪念品**三选一方案——重做必须说明**不可逆风险**与将占用的剩余材料、给出新承诺交付；方案经**主人本人确认**后，**费用调整自动落已确认费用项并同步财务、计入最终费用，制作排期（承诺交付）同步更新，重做占用剩余材料并递减可重做次数**（材料不足时禁止选重做）；重做/替代成品由**制作主管复核**（可退回重做），通过后由**家属 1~5 星评价**结案，处理结果直接影响最终费用与家属评价。失败处理未闭环（待拟方案/待确认/制作中/待复核/待评价）会阻止工单完结。
8. **骨灰盒寄送破损**：登记快递单号 → 在途 → 家属反馈破损（照片+描述，触发关怀回访）→ 补发新单号 → 送达 → 家属确认完好签收。
9. **寄存到期未续费**：柜位 30 天内到期标记 `expiring` 并生成续费提醒；已过期标记 `expired` 并生成跟进；续费后自动关闭待办提醒。
10. **多门店 / 医院转介**：员工数据按门店隔离，管理者可看全部门店；主人下单可选转介医院。
11. **费用与财务**：基础报价与每次变更分行留痕，变更项需家属确认；财务登记收款/退款；完结前校验结清。
12. **见证材料与追溯**：每个交接节点（接运、入冷藏、告别、入炉、出炉、证明、寄送、入柜、回访…）都有操作人、角色、承诺时间、实际时间、备注、照片/视频 URL，时间线中异常（⚠）与已闭环（✓）一目了然。
13. **服务后留存**：交接照片、火化证明编号、寄存位置、寄送单号、费用明细、情感回访记录全部沉淀在工单详情。

### 本次开发实际验证结论

- `tsc -p` 后端全量编译通过；`next build` 前端生产构建通过（11 个路由全部生成）。
- `npm run seed`：2 门店、**16 账号**（新增 2 号店制作人 art2、制作主管 artm1/artm2）、冷藏/火化炉/告别室/24 柜位写入成功；新增 `memento_failure_cases` 表自动建出。
- `npm run demo`（真实 HTTP，重播种后运行）：两单业务全流程跑通，首单 `completed`，时间线 **39 个**可追溯节点，待回访 4 项；管理者总览返回 `open_failure_cases=0`、失败处理家属评分均值。
- **失败处理专项规则（12 项断言全过）**：
  - 材料不足（剩余可重做 0 次）时客服拟「重做」被 `400` 拦截；
  - 退款方案费用为非负数被 `400` 拦截；替代方案不填名称被 `400` 拦截；重做不填不可逆风险/材料占用被拦截；
  - 失败方案客服代确认返回 `403`，仅主人本人可确认；2 号店制作主管访问 1 号店工单 `403`；
  - 失败处理「制作中 / 待主管复核 / 已复核待评价」三种未闭环状态分别调用完结均被 `400` 拦截；家属评价结案且财务结清后才允许完结；
  - 主人确认后费用调整自动成为**已确认**费用项（验证到 -30 元 memento 项）并计入最终应收，制作单排期 `due_at` 同步、重做材料份数与剩余次数正确递减。
- 空库播种脚本 `npm run seed:ifempty`：已有数据时输出「跳过自动播种」，容器重启不覆盖业务数据。
- 手动 SQL 将柜位到期时间改为昨天后调用 `POST /api/lockers/scan`：柜位标记 `expired` 并生成「到期未续费」回访；续费后恢复 `occupied`、回访关闭。
- 前端生产模式 `next start` 冒烟：`/login` 返回 200 且含新增「制作主管 · 苏晴」一键体验入口。

前端页面的操作通过后端 API 闭环验证；图形界面建议按 `demo-flow` 的顺序在浏览器点验一遍：
`owner1` 下单 → `cs1` 核定+调度 → `driver1` 延误/接运 → `owner1` 确认费用/改期/确认失败方案 →
`rite1` 告别 → `fire1` 火化 → `art1` 失败立案（材料/主人选择）→ `cs1` 拟重做/退款/替代方案 →
`owner1` 确认方案与评价 → `artm1` 复核 → `fin1` 核对费用收款 → `cs1` 完结 → `manager1` 看总览（失败处理/评分卡片）。
